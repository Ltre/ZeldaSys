# ZeldaSys 第一轮需求讨论稿（v0）

> 状态：Idea / 需求讨论中  
> 日期：2026-10-04  
> 工作分支：`dev/2610-s1`  
> 来源：`doc/prompt/dev-prompt-log/first.md`  
> 本文不是正式开发路线，不应视为 `doc/roadmap/master` 的实施承诺。

## 1. 已确认的项目约束

目前已明确：

1. 产品核心方向是实现一个类似《塞尔达传说：王国之泪》究极手能力的“组合 / 建造”系统。
2. 用户可以自定义材料（下文暂时把可参与建造的基本对象统一称为“零件 / Part”，避免“材料”同时表示木头、金属等材质属性和一个可摆放物体）。
3. 最终客户端目标平台包括 Android、iOS、PWA、Windows、Linux、macOS。
4. 第一阶段优先 PWA 与 Android。
5. 服务端技术如果需要则使用 Node.js。
6. 第一阶段不为了“架构完整”而强行引入服务端；只有出现云存储、账号、多端同步、共享等明确需求时才增加服务端。
7. 正式开发路线尚未确定。当前阶段的产物存放在 `doc/prompt/idea/first/`，只有需求和技术边界充分收敛后，才把具体开发步骤写入 `doc/roadmap/master/`。

## 2. 当前对产品的建议定义

第一阶段建议把 ZeldaSys 定义为：

> 一个离线优先、单用户、可自定义零件的 3D 建造沙盒。用户从零件库中选择零件，在 3D 空间中移动、旋转、缩放并建立连接，形成一个可保存、再次编辑的组合体。

这里刻意不把首版定义成“完整游戏”。建造系统本身应该先成为一个独立、可验证的核心能力，之后再决定是否叠加人物、地图、任务、战斗、资源消耗等游戏系统。

第一阶段也不建议直接把“像王国之泪”理解为复制其所有物理规则。真正需要复现的是体验骨架：

- 选取对象；
- 在 3D 空间中操纵对象；
- 靠近其它对象时得到清晰的连接反馈；
- 建立连接；
- 多个零件形成一个组合体；
- 可以解除连接并继续编辑；
- 组合结果可保存、加载；
- 手机触控操作也能完成上述闭环。

## 3. 建议先统一的领域术语

为了减少后续数据结构与 UI 文案混乱，建议暂定以下术语。

### 3.1 PartDefinition：零件定义

描述“零件库里的一种零件是什么”。

可能包含：

- 名称；
- 分类；
- 3D 几何来源；
- 默认尺寸；
- 外观 / 材质；
- 质量；
- 碰撞形状；
- 可连接区域或吸附点；
- 用户自定义参数；
- 缩略图；
- 版本号。

例如“木板”是一种 PartDefinition。

### 3.2 PartInstance：零件实例

用户把一种零件拖入建造场景后，产生一个实例。

至少包含：

- 唯一 ID；
- 对应的 PartDefinition ID；
- 位置；
- 旋转；
- 缩放；
- 当前连接关系；
- 实例级覆盖参数。

同一种木板可以在场景中出现很多次，每一块都是独立 PartInstance。

### 3.3 Connection：连接

表示两个零件实例之间的连接关系。

至少需要描述：

- A 零件；
- B 零件；
- A 上的连接位置；
- B 上的连接位置；
- 连接类型；
- 相对姿态；
- 是否允许旋转 / 滑动；
- 如启用物理时的强度等参数。

### 3.4 BuildDocument：建造文档

一次建造工程的完整可保存状态。

建议至少包含：

- 文档 ID；
- 名称；
- 版本；
- 所有 PartInstance；
- 所有 Connection；
- 相机 / 视角等编辑器状态（是否持久化待定）；
- 创建 / 修改时间；
- 所使用的自定义 PartDefinition 引用。

## 4. 第一阶段建议的产品闭环

首个可用版本建议只追求以下闭环：

1. 打开应用；
2. 新建一个建造工程；
3. 从零件库添加零件；
4. 在 3D 空间中平移、旋转零件；
5. 把两个零件连接；
6. 重复添加和连接，形成组合体；
7. 可以解除连接；
8. 可以撤销 / 重做；
9. 本地保存工程；
10. 关闭应用后重新加载并继续编辑。

只要这个闭环在 PWA 与 Android 上都可靠，ZeldaSys 的核心方向就已经能够被实际验证。

## 5. “用户自定义材料 / 零件”的需求分层

这是目前最关键、也最容易让项目复杂度失控的需求，建议拆成三个等级讨论。

### Level A：参数化基础零件

用户从系统内置形状创建零件，例如：

- 长方体 / 木板；
- 圆柱；
- 球；
- 圆盘；
- 杆件。

用户可以修改：

- 名称；
- 长宽高 / 半径等尺寸；
- 颜色或基础材质；
- 质量等少量物理属性；
- 连接点。

优点：首版实现成本和跨平台风险最低。

### Level B：导入标准 3D 模型

允许用户导入 glTF / GLB 等模型，并为其配置：

- 缩放；
- 碰撞体；
- 质量；
- 连接点；
- 缩略图和分类。

这会明显提高“自定义”的实际价值，但会带来模型大小、性能、碰撞体生成、移动端文件权限等问题。

### Level C：完整零件编辑器

应用内直接提供网格建模、复杂碰撞编辑、材质节点、脚本等能力。

这一层已经接近一个小型 3D 编辑器，不建议进入第一阶段。

### 当前建议

MVP 先实现 Level A；架构和数据格式预留 Level B，不在首版承诺 Level C。

待用户确认：首个公开可用版本是否已经必须支持导入自己的 GLB / glTF。

## 6. 连接系统的三个候选方向

连接方式直接决定“王国之泪感”以及物理引擎复杂度，目前应尽早确认。

### 方案 A：自由表面粘合

用户让两个物体表面靠近后，系统按接触点直接固定。

优点：

- 最接近“哪里都能粘”的直觉；
- 不要求每个零件预先配置大量连接点。

难点：

- 吸附姿态计算更复杂；
- 移动端很容易出现“想连这里却吸到别处”；
- 物理连接稳定性更难保证。

### 方案 B：预定义 Snap Point

每个零件定义若干连接点，靠近时点对点吸附。

优点：

- 最容易做出稳定、可预测的移动端体验；
- 保存格式清晰；
- 连接关系容易调试。

缺点：

- 自由度较低；
- 自定义零件必须配置连接点。

### 方案 C：混合模式

普通表面可以自由粘合；有 Snap Point 时优先精确吸附。

长期体验最好，但首版复杂度最高。

### 当前建议

原型阶段优先方案 B 验证完整闭环，同时在 Connection 数据结构中不要把连接永久限制为“点对点”，以便后续演进到方案 C。

待用户确认：更重视“任意位置都能连接”的自由度，还是更重视“手机上容易操作且结果稳定”。

## 7. 物理模拟需要单独决定

“能把零件连起来”与“组合体具有实时刚体物理”是两层能力，不应该默认绑定。

### 不做实时物理时

系统仍然可以支持：

- 碰撞辅助；
- 对齐；
- 吸附；
- 连接；
- 组合体保存；
- 编辑。

这种模式本质是 3D 装配编辑器，首版风险明显较低。

### 做实时物理时

还要处理：

- 重力；
- 刚体；
- 碰撞；
- 固定关节；
- 铰链；
- 质量；
- 休眠；
- 穿透；
- 高速运动；
- 大型组合体稳定性；
- 移动端性能。

如果还要实现“轮子、风扇、马达”等功能零件，则会继续增加执行器、控制输入和关节约束。

### 当前建议

把“编辑态”和“模拟态”分离：

- 编辑态：用于稳定摆放和连接，不让物理不断打断用户操作；
- 模拟态：用户主动点击“运行 / 模拟”后才启用重力和刚体行为。

但首个 MVP 是否必须包含模拟态，仍待确认。若目标是尽快验证建造 UX，可以先不做实时物理。

## 8. 功能零件建议后置

王国之泪式建造的乐趣很大一部分来自轮子、风扇、转轴等功能件，但它们应建立在稳定的零件、连接、保存和物理模型之上。

未来可能存在：

- 轮子；
- 风扇 / 推进器；
- 马达；
- 铰链；
- 滑轨；
- 弹簧；
- 开关；
- 电池 / 能量源；
- 逻辑控制件。

第一阶段不建议承诺这些功能全部存在。可以在核心系统验证后挑 1～2 个作为“系统可扩展性”的验证样例。

## 9. PWA / Android 的交互约束

首版不是先做桌面再硬塞到手机，而应从一开始按触屏设计。

建议至少支持：

- 单指：选择 / 拖动；
- 双指：旋转视角、缩放视角；
- 明确的“移动 / 旋转”模式切换，避免手势冲突；
- 选中物体后的轴向 / 平面约束；
- 吸附预览；
- 连接成功的视觉反馈；
- 删除、复制、解除连接；
- 撤销 / 重做。

桌面端后续可以增加鼠标键盘快捷操作，但不能让核心操作依赖右键或键盘。

## 10. 本地数据优先

在没有账号 / 云同步需求前，建议所有核心能力可以完全离线工作。

需要本地保存的数据主要有：

- BuildDocument；
- 用户自定义 PartDefinition；
- 用户导入的模型资源（若后续进入 Level B）；
- 设置项。

PWA 可考虑 IndexedDB 等浏览器持久化机制；Android 包装层应优先复用同一份业务数据格式。

无论最终使用哪种存储实现，建议尽早定义与存储介质无关的可版本化 JSON Schema，避免未来增加 Node 服务端时被本地实现绑死。

## 11. 服务端的触发条件

现阶段建议明确“不需要 Node 服务端”作为默认状态。

出现以下任一正式需求后再设计服务端：

- 用户账号；
- 多端同步；
- 云备份；
- 分享链接；
- 公共零件库；
- 多人协作；
- 权限管理；
- 作品发布 / 社区；
- 服务端模型转换；
- 大文件云存储。

这样可以避免首版同时维护客户端、API、鉴权、数据库和部署基础设施。

## 12. 当前建议排除在 MVP 外的范围

为了尽快验证核心系统，暂不建议把以下内容列为第一版必需：

- iOS；
- Windows / Linux / macOS 原生打包；
- 登录注册；
- 云同步；
- 多人实时协作；
- 社区 / 市场；
- 完整游戏世界；
- 角色移动与战斗；
- 任务系统；
- 资源采集；
- 复杂破坏系统；
- 材料耐久；
- 任意脚本；
- 应用内完整网格建模；
- 超大型场景；
- AR。

这些能力不是永久排除，只是不应在需求尚未验证时进入首个开发闭环。

## 13. 建议的 MVP 验收定义（候选）

以下不是正式 roadmap，只是用来帮助讨论“什么叫第一阶段做成了”。

一个候选 MVP 可以被认为成立，当用户能够在 PWA 和 Android 上：

1. 新建 / 打开一个本地工程；
2. 使用至少 3 种基础零件；
3. 自定义至少尺寸和外观；
4. 在 3D 空间稳定选择、平移和旋转零件；
5. 连接两个或多个零件；
6. 解除已有连接；
7. 复制 / 删除零件；
8. 撤销 / 重做关键编辑操作；
9. 保存后退出；
10. 再次打开后结构、姿态和连接关系完全恢复。

如果首版要求物理，则再增加：

11. 手动进入模拟态；
12. 组合体在重力 / 碰撞下保持合理连接；
13. 退出模拟态后可恢复到可编辑状态（具体恢复语义待定）。

## 14. 对技术架构的早期约束，而不是选型结论

正式技术栈暂不在本文拍板，但需求层面可以先定几个原则：

- 核心领域模型不要绑定 DOM、Android 或具体渲染引擎；
- PWA 与 Android 尽量共享绝大多数业务代码；
- 项目文档格式、零件格式、连接格式必须版本化；
- 编辑命令最好支持可逆操作，为撤销 / 重做和未来协作打基础；
- 渲染状态与持久化领域状态分离；
- 物理引擎状态不应成为唯一事实来源；
- 服务端未来出现时，客户端离线数据仍应能独立存在。

“是否采用 TypeScript + Web 3D 引擎 + PWA + Android Web 容器 / Capacitor 一类方案”属于下一轮技术路线比较内容，暂不写入正式 roadmap。

## 15. 下一轮必须讨论的问题

以下问题会直接改变 MVP 规模，应优先得到明确答案：

1. **产品形态**：ZeldaSys 最终更像“建造工具 / 沙盒”，还是会发展成一款有角色和世界的游戏？
2. **自定义零件**：第一版只需参数化基础形状，还是必须允许用户导入 GLB / glTF？
3. **连接自由度**：首版可以接受 Snap Point，还是必须从一开始支持任意表面自由粘合？
4. **物理要求**：首个 MVP 必须能运行重力和碰撞，还是先把装配编辑器做顺？
5. **功能零件**：首版是否至少需要一个“能动”的功能件，例如轮子或马达？
6. **建造规模**：典型作品预计 10～50、100～500，还是上千个零件？这会显著影响渲染、物理和存储设计。
7. **精确编辑**：是否需要输入数值坐标 / 角度 / 尺寸，还是以触控直觉操作为主？
8. **自由缩放**：实例是否允许任意缩放，还是尺寸变化只能通过编辑 PartDefinition？
9. **资源语义**：“材料”除了一个可摆放零件外，是否还需要木材 / 金属 / 石头之类物理材质属性影响质量、摩擦、强度？
10. **分享需求**：近期是否已有“导出一个文件给别人打开”的需求？这不需要服务端，但会影响项目包格式。

## 16. 当前推荐的讨论顺序

为了避免同时讨论 UI、引擎、物理和云端，建议依次确认：

1. 产品形态；
2. 自定义零件层级；
3. 连接模型；
4. 是否需要实时物理；
5. MVP 建造规模；
6. MVP 功能清单与明确非目标；
7. 数据模型；
8. 客户端技术路线；
9. 只有前述内容稳定后，再形成 `doc/roadmap/master` 的开发步骤。

## 17. 当前阶段结论

现在已经足够确定的是：ZeldaSys 首先要验证“自定义零件 + 3D 操作 + 连接 + 本地持久化”这一核心建造闭环，并以 PWA / Android 为第一优先平台；Node 服务端暂不应成为前置依赖。

现在还不足以确定正式开发路线，尤其是“任意表面连接、实时物理、用户模型导入”这三个需求都会显著改变底层方案。因此本文先作为需求讨论基线，下一轮围绕第 15 节的问题收敛后，再决定是否开始写 `doc/roadmap/master`。
