# ZeldaSys 第一轮需求讨论稿（v1）

> 状态：Idea / 需求已明显收敛，尚未进入正式 roadmap  
> 日期：2026-10-04  
> 工作分支：`dev/2610-s1`  
> 前一版本：`requirements-discussion-v0.md`

## 1. 本轮已确认结论

### 1.1 产品定位

前期产品定位为纯建造沙盒 / 工具，不先做角色、地图、任务、战斗等完整游戏系统。

长期方向允许继续扩展：

- 自定义角色；
- 自定义地图；
- 更完整的游戏世界；
- 在建造系统之上增加玩法层。

因此首版架构需要避免把“建造编辑器”写死成某一个固定地图或某一个固定角色的子系统。

### 1.2 首发平台

首轮试水平台：

- PWA；
- Android。

其它平台 iOS、Windows、Linux、macOS 保留为长期目标，但不进入第一轮实现范围。

### 1.3 自定义零件

首版不能只支持长方体、圆柱等参数化基础几何。

还必须支持“类似 SVG 的导入”，即允许用户通过二维矢量轮廓定义自有形状，再转化为可参与 3D 建造和物理模拟的零件。

当前把该能力暂称为：

> SVG-style 2D Vector Part Import

这里暂不等同于“完整支持 SVG 标准的所有特性”。具体输入格式、SVG 子集、二维到三维的转换规则、厚度和碰撞体生成方式仍需继续讨论。

GLB / glTF 导入暂不进入首版，后续再评估。

### 1.4 连接模型

首版必须支持类似《王国之泪》的任意表面连接，不能只依赖预先配置好的 Snap Point。

用户应能够：

1. 拿起一个零件；
2. 把零件的某个表面 / 位置靠近另一个零件；
3. 系统识别候选接触位置；
4. 预览连接后的姿态；
5. 用户确认后，在该接触位置建立连接；
6. 连接后的结构进入物理模拟时仍保持约束；
7. 用户之后可以解除该连接。

Snap Point 可以作为未来提高精确度或特定零件交互的补充，但不是首版连接模型的基础限制。

### 1.5 实时物理

首个 MVP 必须包含实时：

- 重力；
- 碰撞；
- 刚体模拟；
- 连接约束。

因此物理引擎属于 MVP 核心基础设施，而不是后续可选模块。

仍建议区分：

- 编辑态：便于用户稳定摆放、旋转和连接；
- 模拟态：启用完整物理行为。

具体是“编辑态完全冻结物理”，还是“编辑态保留部分碰撞 / 约束”，待技术验证。

### 1.6 功能零件

首版必须包含会主动产生运动或力的功能零件，至少覆盖以下类别：

- 轮子；
- 马达；
- 风扇。

这些功能件不能只是视觉模型，必须能实际参与物理系统。

初步语义候选：

- 轮子：通过旋转关节与其它结构连接，可自由转动或被马达驱动；
- 马达：向旋转关节施加目标速度 / 扭矩；
- 风扇：沿自身方向持续施加推力。

最终控制方式、参数范围、能量系统是否存在，尚待确认。

### 1.7 典型建造规模

首版典型作品规模约为：

> 50 个零件。

首版设计和性能验证优先保证约 50 个零件、多个物理连接以及少量功能零件同时工作的体验。

该数字是典型目标，不表示必须硬限制最多只能存在 50 个零件。

## 2. 修订后的 MVP 产品闭环

当前候选 MVP 应至少支持：

1. PWA / Android 启动应用；
2. 新建本地工程；
3. 添加参数化基础零件；
4. 导入 SVG 风格二维矢量形状并生成自定义零件；
5. 选择、移动、旋转零件；
6. 在任意表面位置进行粘合连接；
7. 解除已有连接；
8. 添加轮子、马达、风扇等功能件；
9. 进入实时物理模拟；
10. 观察重力、碰撞、刚体和连接约束；
11. 功能件能够实际驱动结构运动；
12. 从模拟返回编辑；
13. 撤销 / 重做主要编辑操作；
14. 本地保存；
15. 完全退出后重新加载，零件、姿态、连接、功能参数能够恢复。

## 3. 对领域模型的影响

原 v0 中的以下核心模型仍然成立：

- `PartDefinition`
- `PartInstance`
- `Connection`
- `BuildDocument`

但需要扩展。

### 3.1 PartDefinition

至少需要能够描述：

- 几何来源类型：primitive / vector-import / future-model-import；
- 渲染网格；
- 碰撞表示；
- 默认质量 / 密度；
- 摩擦、恢复系数等基础物理参数；
- 是否为功能零件；
- 功能零件类型与参数；
- 数据格式版本。

### 3.2 Connection

任意表面连接意味着 Connection 不能只存 Snap Point ID。

至少应考虑保存：

- part A ID；
- part B ID；
- A 局部坐标系中的 anchor；
- B 局部坐标系中的 anchor；
- 接触法线 / 连接朝向；
- 建立连接时的相对姿态；
- constraint 类型；
- 功能关节参数（若连接不是固定焊接）；
- 数据版本。

普通“粘合”首版可映射为固定约束 / weld-like constraint。

轮轴 / 马达则可能需要 revolute / hinge 一类约束。

### 3.3 物理状态与工程状态

仍坚持：

> 物理引擎内部状态不能成为唯一持久化事实来源。

保存工程时应保存领域状态和必要的物理参数，再由加载过程重建物理世界。

否则未来更换物理引擎、修改版本或跨平台时会非常困难。

## 4. SVG 风格导入的技术含义

这是下一轮最优先需要收敛的需求。

二维矢量图要进入 3D 刚体世界，一般需要经过类似流程：

`2D path -> 标准化轮廓 -> 三角化 -> 赋予厚度 / 挤出 -> 生成渲染 mesh -> 生成 collider`

首版应优先明确以下问题：

1. 是否直接接收标准 `.svg` 文件，还是定义一个更小的 SVG-like JSON / path 格式；
2. 支持哪些元素：path、polygon、rect、circle、ellipse 等；
3. 是否支持孔洞；
4. 是否支持 stroke，还是只处理闭合 fill；
5. 是否支持 transform；
6. text、filter、mask、clipPath 等复杂 SVG 特性是否明确不支持；
7. 二维形状如何得到三维厚度；
8. 用户能否调整厚度；
9. SVG 单位如何映射到世界单位；
10. 凹多边形碰撞体如何处理；
11. 是否需要自动凸分解，还是使用多个简单 collider；
12. 导入后能否继续编辑原始二维轮廓。

首版建议追求“确定的、有限的矢量轮廓子集”，而不是以兼容浏览器 SVG 渲染器为目标。

## 5. 任意表面粘合的技术含义

首版连接体验建议围绕以下过程设计：

1. 用户操纵 source part；
2. 通过 raycast / shape cast / closest-point 等方式寻找 target surface；
3. 得到接触点与表面法线；
4. 计算 source part 的候选姿态；
5. 显示吸附 / 粘合预览；
6. 用户确认；
7. 将世界空间接触点转换为双方局部 anchor；
8. 创建固定物理约束；
9. 保存 Connection；
10. 模拟时由物理引擎维持约束。

需要重点验证：

- 凹形物体表面命中；
- 两个物体已经穿透时如何修正；
- 多个邻近表面时怎样选候选点；
- 手机触控如何精确指定粘合位置；
- 多连接形成闭环时物理求解是否稳定；
- 50 零件规模下约束数量的性能。

## 6. 功能零件的初步系统边界

首版至少存在三类行为：

### 6.1 Wheel

- 有旋转轴；
- 能作为滚动接触物；
- 可自由转动；
- 可与马达机制组合。

### 6.2 Motor

候选模型：

- 绑定某个旋转关节；
- 提供目标角速度；
- 提供最大扭矩；
- 支持启停；
- 后续可扩展正反转 / 用户控制。

### 6.3 Fan

候选模型：

- 沿局部固定方向产生力；
- 可设置推力大小；
- 力作用在自身刚体或所属组合体上；
- 支持启停。

第一版暂不默认引入电池、能源消耗或复杂逻辑电路，除非后续明确要求。

## 7. 性能基线

典型 50 零件意味着首版性能验证至少应覆盖：

- 约 50 个同时存在的刚体；
- 多个固定连接；
- 若干旋转关节；
- 至少数个持续施力 / 驱动的功能件；
- 移动端触控与渲染同时工作；
- PWA 与 Android 的相同工程可加载。

后续 roadmap 需要给出明确测试场景，而不能只写“优化性能”。

## 8. 服务端结论保持不变

当前仍不需要 Node 服务端。

在出现下列需求前保持客户端离线优先：

- 账号；
- 云同步；
- 云备份；
- 分享平台；
- 多人协作；
- 公共素材库。

本地工程数据格式需要从第一版就版本化，为未来服务端同步预留空间。

## 9. 当前不进入首版的内容

已明确暂缓：

- GLB / glTF 自定义模型导入；
- 自定义角色；
- 自定义地图；
- 完整游戏世界；
- iOS 原生交付；
- Windows / Linux / macOS 桌面交付；
- 云端账号与同步；
- 多人协作；
- 社区系统；
- 完整 SVG 标准兼容；
- 应用内完整 3D 网格建模。

## 10. 进入正式 roadmap 前仍需确认的问题

当前剩余问题已经从“大方向”缩小到实现语义。

### A. SVG 风格导入

需要确定首版输入规范。

### B. 功能件控制

需要确定：

- 马达如何开关；
- 马达速度 / 扭矩用户如何设置；
- 风扇如何开关；
- 是否有全局“激活装置”按钮；
- 是否首版需要交互控制映射。

### C. 编辑态与模拟态

需要确定：

- 进入模拟后结构发生位移，退出模拟时是否保留最终位置；
- 还是恢复进入模拟前的编辑快照；
- 编辑态是否允许零件互相穿透；
- 编辑态是否启用碰撞辅助。

### D. 任意表面粘合的姿态规则

需要确定：

- 粘合时是否自动让两个接触面平行；
- 是否保持用户当前旋转，只把接触点贴上去；
- 是否允许连接后绕法线调整角度；
- 是否需要吸附距离阈值；
- 是否需要粘合预览和确认动作。

## 11. 当前是否进入 roadmap

结论：**暂不进入正式 `doc/roadmap/master`。**

原因不是大方向不明确，而是上面 A-D 会直接决定：

- 几何处理库；
- 物理引擎使用方式；
- Connection 数据结构；
- 编辑器状态机；
- 第一阶段测试用例。

建议再完成一轮针对 A-D 的需求讨论，即可开始技术选型与正式 roadmap。

## 12. 当前产品基线一句话

> ZeldaSys 首版是一个 PWA / Android 优先、离线优先的 3D 物理建造沙盒，支持参数化零件和 SVG 风格二维形状导入、任意表面粘合、实时刚体物理，并提供轮子、马达和风扇等可动功能件；典型建造规模约 50 个零件。
